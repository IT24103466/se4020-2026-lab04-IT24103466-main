
Lab 04 - Exercise 2: Parallel summation  S = sum_{i=1..N} [ i - i^2 + sqrt(2*(i+1)) ],  N = 10,000,000

Compile and run:
    gcc -O2 -fopenmp lab04b.c -o lab04b.o -lm
    ./lab04b.o <threads>

Hardware: Intel Core i5-8365U, 4 physical cores, 2 hardware threads per core = 8 logical CPUs.
    Configuration A (small): 1 physical core, 2 hardware threads  (taskset -c 0,4)
    Configuration B (large): 4 physical cores, 8 hardware threads (all CPUs)

------------------------------------------------------------------------------
Parallelisation
------------------------------------------------------------------------------
Each term depends only on i, so the iterations are independent. The only shared
data is the running total S, so the update of S must be protected. Terms are computed
in double precision (i*i would overflow an int).

Critical section:
    #pragma omp parallel for
    for (long i = 1; i <= N; i++) {
        double d = (double)i;
        double v = d - d*d + sqrt(2.0*(d + 1.0));   // private to each thread
        #pragma omp critical
        S += v;
    }

Atomic section: identical, but with "#pragma omp atomic" in front of S += v;

(For comparison a reduction(+:S) version was also timed.)

------------------------------------------------------------------------------
Correctness
------------------------------------------------------------------------------
All versions (serial, critical, atomic, reduction) give S = -3.333333e+20 for every thread
count on both configurations. This agrees with the closed form
    sum(i - i^2) = -(N-1)N(N+1)/3 = about -3.333333e20  (the sqrt terms add only about 3e10,
which is far below the printed precision).
So the mutexes remove the data race and the answer is correct.

------------------------------------------------------------------------------
1. How does the parallel program perform?
------------------------------------------------------------------------------
- Critical and atomic are correct but much slower than the serial program (speedup
  between 0.01 and 0.16, i.e. a slowdown of 6 to 100 times). Each iteration only does a
  few arithmetic operations and a square root, which is cheaper than acquiring the lock or
  doing the atomic update on the single shared variable S, so the threads spend most of
  their time waiting for each other (contention) and moving the cache line that holds S
  between cores.
- On Configuration B the time of critical and atomic gets worse as threads are added
  (critical 0.14 s with 1 thread to 1.38 s with 16 threads), because more cores really
  compete for the same lock. On Configuration A the time stays about constant (0.13 to
  0.15 s) because only 2 hardware threads on one core can run at a time.
- Atomic is faster than critical at 1 thread (0.095 s against 0.141 s) because it uses a
  single hardware instruction instead of a lock. With many threads the two are similar.
- The reduction version, where every thread adds into a private partial sum and the
  partial sums are combined once at the end, scales well: speedup 2.07 with 2 threads and
  3.78 with 4 threads on Configuration B (matching the 4 physical cores). With 8 and 16
  threads there is no further gain because there are only 4 physical cores (the extra
  hardware threads share a core's execution units). On Configuration A (one core) it
  stays at about 1.0, as expected.

Conclusion: critical and atomic sections guarantee the correct sum but, when used on
every iteration, they destroy the speedup. To obtain a real speedup the synchronisation
should be done once per thread (private partial sums / reduction) instead of once per
iteration.
